这次核心的修改是围绕着把我们项目的核心功能冰洗预测模型给接入到通用智能体框架中，
即generic agent + icewash model的架构，同时要符合我们的之前的展望，就是平台的高扩展性，因此icewash预测模型是作为一个基础服务独立运行的，开发阶段和部署阶段都是如此；
然后我们agent这边可以接受为每个service model定制工具；
agent这边需要根据service model的响应类型调整前端展示方案；
icewash model需要接口化，预测处理需要能够异步执行；
icewash model需要提供的功能包括：
history: 查询历史销量，用户描述品类，时间，然后经过llm包装请求后向icewash model发送得到结果，处理后由前端展示，此时前端展示的组件为用户友好的查看历史销量的数据看板
forecast:查询未来销量，用户描述品类，时间，然后经过llm包装请求后向icewash model发送得到结果，处理后由前端展示，此时前端展示的组件为用户友好的查看未来预测销量的数据看板
explain:白盒归因，解释未来销量，用户查询未来销量之后，返回得到的不仅是未来销量的结果，同时还有当前预测结果的成因，这个功能应该是和forecast绑定的，也就是只要forecast了就会同时返回explain的结果，处理后由前端展示，此时前端展示的组件为用户友好的查看未来预测销量的，同时能看到每个具体因子的影响变化的数据看板，同时要产出一份预测分析报告（这部分设立一个template之后由llm来写），可以参考冰箱预测分析报告_202608.md	冰箱预测结果的 markdown 分析报告和洗衣机预测分析报告_202608.md	洗衣机预测结果的 markdown 分析报告
simulate:正向推导，用户发送消息，如果我调整了某某销售策略，商品价格，之后，后端能够解析到具体的预测模型的变量，然后用现有模型跑出来一次模拟，之后返回数据，这个过程是异步处理的，icewash model和后端通过taskid的方式交互，冰洗预测模型跑完结果之后放在本地，后端通过taskid 查询任务状态，如果好了就返回结果，防止超时，这个过程中前端先响应一部分说已经在处理了，然后下面也在转圈轮询等待；
optimize:逆向优化，用户发消息，如果我想要某某品类，某个时间段的销量达到多少，那我最好的策略应该是怎么办，消息发送到后端之后，llm要能够解析到能发送给icewash model的具体执行参数，然后他也是异步计算之后返回结果，逆向优化的方案目前icewash model内部的策略（先简单实现）是给定了预先设立的优化方案的优先级，然后挨个尝试之后给出一个最优解，这个说实话我不知道模型里面这块功能做好了没有，但是我们设想的架构是这样的；
这次优化可以改动现有的接口，后端的，冰洗预测模型的基础服务的都可以改，
